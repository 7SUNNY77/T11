# Дрейф API инструментов в мультиагентной LLM-системе — этап 1

Каркас эксперимента: как изменения API инструментов влияют на МАС (Planner → Executor → Verifier)
и помогает ли агентам changelog. Сетка: версии API {v1, v2_contract, v2_contract_stale, v2_units,
v2_benign} × осведомлённость {A0 — без changelog, A1 — changelog в промпте Executor}.

| Версия | Что меняется | Что видит агент |
|---|---|---|
| v1 | базовая | схема v1 |
| v2_contract | `nights` → `num_nights`, `price` → `price_total` | обновлённая схема |
| v2_contract_stale | то же, что v2_contract | **схема v1**: обёртку инструмента не обновили |
| v2_units | цены в центах (×100) | схема v1, она не изменилась |
| v2_benign | новые необязательные поля и параметр `sort_by` | обновлённая схема |

Для A1 у v2_contract_stale тот же changelog, что у v2_contract; у v1 — нерелевантный (car_rental).
Контраст v2_contract и v2_contract_stale показывает, что выдерживает LLM-агент при свежей схеме
и что при устаревшей. В пилоте Gemini при свежей схеме сразу вызвал `num_nights`, проигнорировав
few-shot под v1.

## Запуск

```bash
# fake-провайдер: проверка логики, пишет только в runs/fake/
python run.py --provider fake --conditions all --n-tasks 30 --repeats 1

# оценка бюджета без вызовов (берёт задержку и токены из реальных трасс, если они есть)
python run.py --provider gemini --estimate

# smoke: одна задача, подробный вывод шагов, без кэша
python scripts/smoke.py --provider gemini --task T01 --version v1 --awareness A0

# пилот: одна задача × все 8 условий, отдельный эксперимент
python run.py --provider gemini --tasks T01 --experiment pilot

# полная сетка
python run.py --provider gemini --conditions all --n-tasks 30 --repeats 1
```

Прочие флаги: `--conditions v1:A0,v2_units:A1`, `--workers N`, `--max-runs N`, `--experiment NAME`.

**Возобновление.** Прогон завершён, если есть `runs/<exp>/<provider>/traces/<run_id>.jsonl`
с записью `run_end`. Повторный запуск той же команды пропускает завершённые прогоны. При исчерпании
дневного лимита (429 «per day») или исчерпании повторов раннер не стартует новые прогоны,
дожидается идущих и выходит с кодом 2 — просто запустите ту же команду позже. Прерванные прогоны
остаются `.jsonl.part` (с `run_aborted`) и перезапускаются. HTTP 400/401/403/404 — ошибка
конфигурации (например, «User location is not supported»): прогон не засчитывается, сетка
останавливается.

## Анализ (этап 2а)

```bash
python scripts/analyze.py --experiment main --provider gemini
```

Пишет `reports/analysis.md` и `reports/success_by_condition.png`. По умолчанию читает завершённые
трассы, поэтому работает, пока сетка ещё идёт: раннер пишет results.csv только в конце или при
остановке. Флаг `--csv` переключает на results.csv. По умолчанию статистика считается только по
**полным блокам** (задача пройдена во всех условиях сетки); `--include-partial` включает все
прогоны. В отчёте:
- число полных блоков и n по каждому условию;
- успешность по условиям с 95% бутстрап-ДИ по задачам (10 000 ресемплов, фиксированный seed),
  по всем задачам и только по задачам с решением;
- парные сравнения по задачам: точный тест Макнемара, таблица переходов и поправка Холма внутри
  каждого семейства — (а) v2_*:A0 против v1:A0, (б) A1 против A0 внутри версии;
- причины провалов, доля ошибок инструментов, LLM-вызовы, токены и cache_hits на прогон;
- «понял, но не сделал» — эвристики по тексту отчёта Executor: для v2_contract_stale:A0 отчёт
  называет `num_nights` или несовпадение схемы, но вызова с `num_nights` нет; для v2_units:A0 отчёт
  упоминает центы или неверные единицы, но цены в отчёте или финальном ответе не переведены.

## LLM-судья (этап 2б)

```bash
python scripts/judge.py --trial --view messages_only   # пробные вызовы: по провалу v2_units:A0 и v2_contract_stale:A0
python scripts/judge.py --view both                    # все провалы, оба режима
python scripts/judge.py --report-only                  # пересобрать отчёты без вызовов
```

Судья `openai/gpt-oss-120b` через Groq (temperature 0, reasoning_effort low, JSON-режим) получает
сжатую трассу провала: запрос, эталон, пронумерованные шаги, финальный ответ. Он не видит условие
и версию API, разметку дрейфа, системные промпты агентов и имя эксперимента; это проверяет тест
и проверка каждого входа во время прогона. Режимы наблюдаемости:
- `full` — с ответами инструментов (первые 5 элементов со всеми полями, ошибки целиком);
- `messages_only` — только сообщения агентов и вызовы с аргументами, без ответов инструментов.

Истина вычисляется из трассы при каждой сборке отчёта. Виноват executor. **Шаг ошибки агента**
(основная метрика): для отклонённого вызова — шаг этого вызова, для изменённого выхода — следующий
шаг executor. **Шаг входа дрейфа** (вспомогательная): где executor получил результат с дрейфом
или ошибку. v1 и v2_benign — без истины. Вердикты: `runs/<exp>/<provider>/judge/<setup>/`, по
файлу на прогон, возобновляемо. Отчёты: `reports/judge.md` (режимы рядом), `reports/judge_samples.md`
(5 случайных прогонов, вердикты обоих режимов) и `reports/judge_results.csv`.

- `summary.md` — ключевые цифры для текста; у каждой указан источник (файл и столбцы);
- `results_used.csv` (полные блоки) и `results_all.csv` (все завершённые прогоны);
- `manifest.json` — модели и все параметры генерации, даты прогонов (UTC), sha256 конфига,
  `world.json` и `tasks.json`, версии промптов и отпечатки версий API, git commit с флагом
  незакоммиченных файлов, версии пакетов;
- финальный график `success_by_condition.png`, а также `analysis.md` и `judge*.md`.

## Конфиг (`config/default.toml`)

- `[experiment]`: seed мира и задач, пул задач (30), версии API, условия осведомлённости,
  `workers` (3), `order_seed`, лимит шагов Executor (8).
- `[awareness.<имя>] changelog_to = [...]` — каким агентам добавить changelog. Новое условие
  (например, `A2 = ["executor", "verifier"]`) — только правка конфига.
- `[providers.<имя>]`: `base_url`, `api_key_env`, `model`, `temperature`, `reasoning_effort`,
  лимиты `rpm`/`tpm`/`rpd`/`tpd` (0 — нет или неизвестен), `cache`.

`run_id` = `<версия>_<условие>_<задача>_r<повтор>_<хэш>`; хэш включает провайдера, модель,
temperature, reasoning_effort, версию промптов, отпечатки мира, задач и определения API.
Любое изменение этих параметров даёт новые прогоны, а не смешивание со старыми.

## Выходные данные

`runs/<exp>/<provider>/`: `traces/*.jsonl`, `results.csv`, `summary.csv`, `meta.json`, `world.json`, `tasks.json`.

**Трасса** (JSONL): `run_start` (условие, задача, эталон, модель, reasoning_effort, время начала UTC,
JSON-схемы инструментов) → `step` на каждый вызов LLM (agent, messages, ответ, tool_calls, токены,
задержка, cached, число HTTP-запросов) → `run_end` (финальный ответ, результат checker'а, счётчики).
Каждый результат инструмента в `tool_results` размечен служебными полями, которых агенты не видят:
`drift_affected`, `drift_type` и `shadow_v1_result` — ответ v1 на тот же вызов.

**results.csv** — одна строка на прогон: условие, задача, `gold_kind`, success, reason, `pair_ok`,
`total_ok`, `json_fenced`, статус Executor, LLM-вызовы, HTTP-запросы, `cache_hits`, токены (включая reasoning),
суммарная задержка, ошибки инструментов, число результатов с `drift_affected`, фактически
полученный changelog по каждому агенту (`none` / `own` / `irrelevant`), время начала.

## Особенности дизайна, которые важно помнить при анализе

- **Общий кэш между условиями — осознанное решение (common random numbers).** Ключ кэша не
  содержит условия. Дословно одинаковые вызовы разных условий одной задачи и повтора получают один
  и тот же ответ модели. Поэтому условия отличаются только самим изменением API или changelog,
  а не случайностью генерации, и парное сравнение (pass→fail по задачам) точнее. Что общее на практике:
  - Planner без changelog в блоке задачи видит одинаковый промпт во всех условиях, план у них один;
  - первый шаг Executor совпадает у условий с одинаковыми схемами и промптом
    (v1, v2_units и v2_contract_stale при одной осведомлённости);
  - любой следующий вызов, пока входы дословно совпадают, например Verifier при одинаковом отчёте.

  Цена: наблюдения внутри блока задачи не независимы, учитывайте это в статистике (парные тесты,
  кластеризация по задаче). Одновременные промахи по одному ключу выполняются один раз, поэтому
  совместность детерминирована и не зависит от гонки воркеров. Столбец `cache_hits` в results.csv —
  число вызовов прогона, ответ на которые взят из кэша. Независимые повторы задаются через
  `--repeats`: `repeat_idx` входит в ключ.
- **Порядок прогонов** — блоками «задача × все условия», перемешанными с `order_seed`. Частичные
  данные сбалансированы по условиям и парные, а дрейф провайдера во времени не совпадает ни с одним
  условием.
- **v2_units и no_option.** Наивный агент видит цены ×100, считает, что всё дороже бюджета,
  и «угадывает» задачи без решения. Успех считайте отдельно по `gold_kind == "pairs"`.
- **PolicyFake** — только тест логики пайплайна, его результаты не являются данными.

## Gemini через OpenAI-совместимый endpoint

- `gemini-2.5-flash-lite` недоступна новым пользователям, используется `gemini-3.5-flash-lite`.
- Gemini 3 кладёт `thought_signature` в `tool_calls[i].extra_content.google`, при параллельных вызовах
  только в первый. Её надо вернуть в истории, иначе следующий запрос получит HTTP 400.
  Клиент возвращает все нестандартные поля tool_call дословно, а поля уровня сообщения пишет
  только в трассу.
- Gemini API недоступен из части регионов (HTTP 400 «User location is not supported»).
- Параметры генерации зафиксированы в конфиге: `temperature = 0.7`, `reasoning_effort = "low"`.
  С `"low"` задержка около 2 с на вызов против 18–25 с на умолчании; узким местом становится RPM.
  Endpoint не сообщает reasoning-токены (`reasoning_tokens` = 0).
  С `"low"` модель часто оборачивает JSON в ```json: checker это допускает и ставит `json_fenced`.
- Бесплатный тариф: 500 запросов в сутки на проект и модель (`GenerateRequestsPerDayPerProjectPerModel`);
  полная сетка из 300 прогонов (~1000 запросов) занимает несколько дней запусков.

## Ограничения

- **Синтетика.** Домен (командировки), задачи и изменения API синтетические и намеренно чистые:
  одно изменение за раз, детерминированный mock, известный эталон. Переносимость на реальные API
  с документацией, версионированием и шумными ответами не проверялась.
- **Одна модель агентов, один повтор.** `gemini-3.5-flash-lite`, `reasoning_effort = "low"`,
  `temperature = 0.7`, `--repeats 1`. Разброс сэмплирования виден уже в данных: v2_units:A0 на T01
  провалился в пилоте и прошёл в основной сетке. Эффекты для других моделей, уровней рассуждений и
  с повторами не оценены.
- **Пилотный объём.** Статистика считается по полным блокам; их число указано в каждом отчёте
  (`reports/summary.md`). Доверительные интервалы при n ≈ 12–30 задач на условие широкие.
- **Зависимость внутри блока.** Общий кэш между условиями (common random numbers) делает прогоны одной
  задачи коррелированными. Парные тесты это учитывают, независимыми наблюдениями считаются только задачи.
- **Атрибуция намеренно лёгкая.** Короткие трассы (4–10 шагов), одна внесённая причина, судья знает
  эталон и то, что прогон провален. Точность судьи в режиме `full` поэтому нельзя сравнивать с
  бенчмарками атрибуции вроде Who&When. Режим `messages_only` показывает, как она падает при снижении
  наблюдаемости; в нём судья во многом пересказывает самодиагностику Executor.
- **Гипотеза о смещении атрибуции вниз по цепочке не проверена.** Во всех текущих провалах ошибка
  видна уже в отчёте Executor, и Verifier на таком входе действует правильно (см. «Следующие шаги»).
- **Эвристики по ключевым словам.** «Понял, но не сделал» и «причина названа» считаются по шаблонам
  текста, без ручной разметки всех случаев. Возможны пропуски: например, «local currency» вместо
  центов. Для проверки есть `reports/judge_samples.md` и примеры в `reports/analysis.md`.
- **Определение истины для судьи — наше.** Виновный агент всегда executor; шаг ошибки определён правилом
  (отклонённый вызов или следующий шаг после изменённого выхода). Для v1 и v2_benign истины нет.
- **Прогоны в разные дни.** Из-за дневного лимита сетка собирается за несколько запусков. Блочный
  перемешанный порядок не даёт дрейфу провайдера во времени совпасть с одним условием, но и не
  устраняет его.

## Следующие шаги

- **Проверка смещения атрибуции: условие «выдача больше не отсортирована по цене».** API продолжает
  возвращать корректные цены в долларах, но список больше не упорядочен по возрастанию; ни схема, ни
  описание не меняются. Executor, приученный few-shot'ом брать первый элемент, выдаст правдоподобный, но
  неверный отчёт: реальные id, реальные цены, валидная сумма в рамках бюджета. Verifier проверяет только
  бюджет, «одобрит» не самую дешёвую пару, и финальный ответ будет неверным без единой видимой ошибки.
  Здесь, в отличие от текущих провалов, последним ошибку «пропустил» Verifier, а отчёт Executor выглядит
  нормально. Это и проверяет гипотезу о смещении вины вниз по цепочке, особенно в режиме `messages_only`.
- Повторы (`--repeats` > 1) и вторая модель агентов — для оценки разброса и переносимости.
- Ручная разметка вердиктов судьи и самодиагностики Executor, чтобы проверить эвристики по ключевым словам.
